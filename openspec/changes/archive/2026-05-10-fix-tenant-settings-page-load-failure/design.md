## Context

Tenant 设置入口由 `TenantLayout` 菜单、`router.tsx` lazy route、`pages/Settings/*` 页面和共享 API/hooks 共同组成。当前用户反馈为“tenant 设置页面加载失败”，可见失败点可能出现在路由懒加载、权限判断、页面初始查询、API 响应契约或错误处理任一环节。

本 change 只处理设置页面不可加载这一可用性问题，不重新设计设置模块，也不改变关键词、评分、OpenRouter、团队管理的业务规则。

## Goals / Non-Goals

**Goals:**

- 复现并定位 Tenant 设置页加载失败的具体根因。
- 保证 `/settings` 根入口以及 `/settings/keywords`、`/settings/scoring`、`/settings/ai-provider`、`/settings/team` 等现有设置子路由可正常渲染。
- 当设置页依赖的接口失败或返回空数据时，页面展示可恢复的错误态或空态，而不是白屏、未捕获异常或无限加载。
- 补充最小验证，覆盖修复过的页面加载链路。

**Non-Goals:**

- 不新增设置功能或入口。
- 不调整租户角色权限模型。
- 不重写设置页视觉设计。
- 不变更评分、关键词、OpenRouter、团队管理的业务语义。
- 不做生产发布、镜像推送或线上数据库操作。

## Decisions

1. **先复现再修复加载链路。**  
   先运行 Tenant 前端类型检查/构建或本地页面 smoke，结合浏览器控制台与网络请求定位失败点。这样可以避免把问题误判为某个设置页面的局部 bug。

2. **优先修复契约与状态处理，不做大范围重构。**  
   如果失败来自字段缺失、query key、权限 key、lazy import、API client 路径或异常状态处理，应在对应最小边界修复；只有确认后端响应与前端契约不一致时，才调整后端 schema/service。

3. **设置子页面保持独立降级。**  
   单个设置子页面的接口失败时，应只影响该子页面，并展示错误提示或重试入口；不应让 Tenant 整体 layout、侧边菜单或其它设置入口不可用。

4. **设置根入口必须有明确去向。**  
   `/settings` 应重定向到默认设置子页，或渲染一个有效的设置首页；不能停留在空 outlet、404、白屏或未捕获异常状态。

5. **验证贴近用户路径。**  
   修复后至少验证相关设置路由可以渲染；若修改 API 契约，补充或运行对应后端测试。优先选择现有测试命令与构建命令，不引入新测试框架。

## Risks / Trade-offs

- **[Risk] 根因可能跨前后端契约。** → 先用控制台错误、network 响应、类型检查和现有测试缩小范围，再决定是否触及后端。
- **[Risk] 只修一个子页面可能遗漏其它设置入口。** → 验证时覆盖所有现有设置子路由，而不是只打开报错页面。
- **[Risk] 错误态过度包装掩盖真实异常。** → 保留可观察的错误日志或 message，同时避免用户界面白屏。
- **[Risk] 活跃 v3 change 也在调整部分设置页。** → 本 change 只修加载失败与可用性，不接管 v3 业务改造任务，实施时如遇冲突先暂停确认。
