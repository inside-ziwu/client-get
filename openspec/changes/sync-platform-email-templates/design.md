## Context

当前平台邮件模板保存在 `platform_email_templates`，租户可见模板保存在 `email_templates`。创建租户时，系统会按租户行业复制当时已启用的同业平台模板；但平台后续新增模板不会自动补发给已有租户。

这次变更面向平台运营人员：在 Admin 端对单个平台邮件模板执行同步，将它补齐到所有同行业租户。租户端仍只看到自己的 `email_templates`，不直接读取平台模板库。

## Goals / Non-Goals

**Goals:**

- 为平台邮件模板提供 Admin 端手动同步动作。
- 同步对象限定为与模板行业一致的租户。
- 同步逻辑幂等：已有副本跳过，缺失副本新增。
- 同步结果返回新增、跳过、目标租户总数等摘要，供 Admin UI 展示。
- 保持租户已编辑模板不被覆盖。

**Non-Goals:**

- 不做租户端平台模板导入入口。
- 不做跨行业同步、租户多选或全量广播。
- 不做自动后台同步、定时任务或平台模板更新下发。
- 不修改现有邮件发送链路和发送计划逻辑。

## Decisions

### Decision 1: Admin 主动同步，而不是自动同步

平台模板同步由平台管理员在模板列表中主动触发。这样同步时机明确，结果可见，也避免平台模板草稿、测试模板或行业配置调整时意外下发。

替代方案是创建或更新平台模板后自动同步。该方案省操作，但会扩大误下发风险，并且更新覆盖策略尚未进入本次范围。

### Decision 2: 只补缺失，不覆盖已有副本

同步时用平台模板 id 判断租户是否已有有效副本。已有副本直接跳过，缺失时新增 `platform_copy` 副本。

替代方案是覆盖已有平台副本。该方案能让租户副本保持最新，但可能覆盖租户编辑过的内容，不符合当前“补漏”目标。

### Decision 3: 同步范围按行业匹配

同步目标租户为 `tenant.industry` 与平台模板 `industry` 一致的租户。该规则沿用创建租户时的复制逻辑，产品行为一致且易解释。

替代方案是允许管理员选择租户。该方案更灵活，但会引入选择器、跨行业语义和误选风险，留作后续独立能力。

### Decision 4: 不新增业务表，但增加并发安全索引

复用现有平台模板与租户模板表，不新增同步记录表或历史表。但需通过 Alembic 迁移新增 partial unique index `ix_email_templates_tenant_platform_active ON email_templates (tenant_id, platform_template_id) WHERE deleted_at IS NULL`，防止并发同步创建重复副本。

替代方案是纯应用层防重（事务内先查后插）。该方案无需迁移，但在并发场景下存在竞态窗口，不如数据库约束可靠。

### Decision 5: 只同步到 active 租户

同步目标租户限定为 `status = 'active'` 的租户。suspended 和 archived 租户不参与同步，避免向已停用租户写入无意义数据。

替代方案是同步到所有租户。该方案更简单但无业务价值，且可能给已归档租户引入意外数据。

### Decision 6: 不复制 body_design 字段

平台模板有 `body_design` jsonb 字段（邮件设计器 JSON），但租户模板表无此字段。同步时只复制 HTML/text 等现有字段，与创建租户时的复制逻辑保持一致。

替代方案是给租户模板表加 `body_design` 列。该改动超出本次"补漏"范围，留作后续能力。

### Decision 7: 批量查询 + 循环 INSERT

同步逻辑先一次 SELECT 查出目标租户中已有副本的 tenant_id 集合，再循环 INSERT 缺失的副本。INSERT 使用 `ON CONFLICT DO NOTHING` 配合 partial unique index，确保并发安全。

替代方案是逐租户查询再插入（N+1）。该方案在租户数多时效率差。另一方案是纯批量 INSERT（单条 SQL），但需动态拼接 VALUES，可读性和审计粒度不如循环 INSERT。

### Decision 8: 同步按钮无确认弹窗

同步按钮点击后直接调用 API，不弹出确认对话框。依赖同步的幂等性保障安全——误触不会创建重复副本，也不会覆盖现有数据。

替代方案是加确认弹窗。该方案更安全但本场景误触成本极低（幂等、只新增不覆盖），且运营频次低，不需额外交互摩擦。

### Decision 9: 响应返回完整明细数组

同步响应的 `created` 和 `skipped` 数组返回全部明细，不做截断或分页。当前 B2B 场景单行业租户数在几十个量级，完整数据对运营透明度更高。

替代方案是截断或分页。该方案在当前规模下属于过度工程化，留到租户数增长到千级时再迭代。

## Risks / Trade-offs

- 同行业但业务语境不同的租户收到模板 → 通过 Admin 主动触发和行业限定降低误发范围。
- 并发重复点击导致重复副本 → partial unique index + ON CONFLICT DO NOTHING 保障数据库层幂等。
- 平台模板未启用仍被同步 → 后端必须拒绝未启用模板，返回明确错误。
- 行业名称依赖精确匹配 → 延续现有创建租户行为；行业标准化不纳入本次范围。
- suspended/archived 租户被同步 → 只查询 active 租户，避免无效写入。
- body_design 丢失 → 租户模板表无此字段，与现有创建租户行为一致，不影响邮件发送。

## Migration Plan

- 数据库迁移：新增 Alembic 迁移，创建 partial unique index `ix_email_templates_tenant_platform_active`。该索引仅用于并发安全，不影响现有查询。
- 发布顺序：Alembic 迁移先发布 → 后端同步接口 → Admin 前端操作按钮。
- 回滚策略：若前端回滚，后端接口可保留不影响现有功能；若后端回滚，前端同步按钮会失败并提示；索引回滚只需 DROP INDEX，不影响数据。
- 生产数据：本 change 不自动修改现有数据；只有平台管理员触发同步时才新增租户模板副本。
