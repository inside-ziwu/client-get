## ② 额外发现（design 未提、会影响落地）

- **A. `scripts/maintain_partitions.py` 没有 `intelligence_articles` 条目**：该脚本只维护 `emails_p` / `audit_logs_p`（`scripts/maintain_partitions.py:47-48`）。design §6（design.md:204）与 implement B2（implement.md:40）说要删它的 `intelligence_articles` 条目，实际只有 `app/db/partitions.py:12,26` 两处要删。顺带：`schema_notes.md:31` 与 `docs/database-schema.md:2072` 对 partitions.py 的描述要同步。
- **B. PR B 迁移落地后不可回退到旧镜像**：Dockerfile 启动序是 `alembic upgrade head` → uvicorn（`backend/Dockerfile:22`），lifespan 第一步 `ensure_partitions`（`app/main.py:34`）对 `_MANAGED` 每张表执行 `CREATE TABLE … PARTITION OF intelligence_articles`。`20260824_0002` 跑过之后，任何仍含旧 `partitions.py` 的镜像（即 PR B 之前的 tag）启动即在 lifespan 崩溃。implement §3 只写了"迁移失败阻断启动"，没写"迁移成功后镜像不能回退到 B 之前的 tag（除非先 downgrade，而 spec 禁止生产 downgrade）"。建议写进 B 的回滚点：回退手段只有前向修复。
- **C. 同一 PR 内新旧 `partitions.py` 与迁移的顺序是安全的**：镜像先跑迁移再起 lifespan，新代码已去掉条目，不会自踩。
- **D. `industry_news_reads.user_id → users(id)` 不带 `ON DELETE CASCADE`，会阻塞物理删用户**：租户端 `tenant_team_service.delete_user`（`app/services/tenant_team_service.py:172-174`）与管理端 `admin_config_service.delete_tenant_user`（`:1119`）都是 `DELETE FROM users`。一旦用户标记过任何已读，删除即 FK 违规。现状已有 9 张表无 CASCADE 引用 `users(id)`（`notifications`、`audit_logs` 等，说明删用户本就会被阻塞），但作为"每用户标记"性质的表，库内同类 `user_roles.user_id` 用的是 `ON DELETE CASCADE`。建议 `user_id … REFERENCES users(id) ON DELETE CASCADE`（`tenant_id` 保持不带，租户不物理删除：全仓无 `DELETE FROM tenants`）。
- **E. 主键生成约定**：design `id uuid PRIMARY KEY` 无默认值，与库内 38 张表一致（应用层 `app/core/ids.py::new_uuid()` 生成 uuid7；7 张表用 `gen_random_uuid()`）。service 的 INSERT 与 seed 脚本都必须在 Python 端生成 id，design §3.3 / §3.6 未写明，实现时别漏。
- **F. 时区类型一致**：design 全部 `timestamptz`，与库内约定一致（仅外部表 `crawl_progress` 用无时区类型）；两库会话时区 UTC / GMT，与 spec「日期窗口在 Python 端算」一致，`:window_start` 需传带时区的 `datetime`（spec `database-guidelines.md:52`）。
- **G. 列长度**：`tenants.industry` 是 `varchar(100)`，design `industry_news_sources.industry varchar(50)` 存的是规范值（`'PCB'`）而非租户原值，不冲突；`title varchar(500)` 与旧 `intelligence_articles.title varchar(500)` 同量级；`dedup_key varchar(40)` 恰好放得下 sha1 十六进制（40 字符），若将来换 sha256 需改列。
- **H. 表名无冲突**：两库 `pg_class` 中 `industry_news%` 对象 0 个。
- **I. RLS 不是新表的要求**：spec `database-guidelines.md:22` 明确 RLS 仅名义启用，新表不需要建 policy；旧 `intelligence_sources` 的两条 policy 随表删除即可，不必单独 DROP。
- **J. 窗口键与排序键不一致的口径提示**（与 5b 相关）：窗口按 `fetched_at`，展示 / 排序按 `published_at ?? fetched_at`。首轮抓取会把站点上 `published_at` 很旧的条目（RSS 常带数十条历史）纳入 90 天窗口并按旧日期沉底；这是产品口径而非 DB 问题，但决定了 5b 的索引取舍，建议在 design 里点明是有意的。
- **K. design §6 文档清理清单不全**：以下 spec / README 位置引用了 PR B 将删除的文件或功能，需一并改写：`.trellis/spec/frontend/directory-structure.md:23`、`state-management.md:3,17`、`quality-guidelines.md:14,16`（都以 `intelligence/page.tsx`、`test/intelligence/` 为范例）、`.trellis/spec/backend/api-guidelines.md:21`（以 `/intelligence-sources/batch-import` 为"静态路由在前"范例）、`error-handling.md:3,18`（以 `intelligence_service.publish_article` 为范例）、`README.md:129`（上线前置步骤②「维护行业情报源」）、`domain-rules.md:20`（「情报摘要」桩）。
