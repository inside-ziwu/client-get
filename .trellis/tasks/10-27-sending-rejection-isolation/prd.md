# 第二实例停发定位与修复方案

## 目标与授权范围
查清第二实例 2026-10-26、27 日发送指标为零及后续不发的原因，并在独立 worktree 完成本地修复。用户已审阅方案并授权本地实现与验证。生产写入、生产迁移、生产修数、真实发信、重启、部署、推镜像、自动修改 `.env`、合并 main 仍未授权。

## 已确认背景
事故证据统一见 research/evidence.md。服务商返回 107/101/101 字符的成功 ID，本地 emails.engagelab_message_id 为 varchar(100)，成功回写事务失败；worker 通用异常分支误记 failed 并安排重发。随后第四封进入 quota_deferred 并暂停域名至北京次日零点。前三封不是三次服务商限流，不能把正常收件人标 invalid。第四封具体上游错误码未在现有输出保留。

## 需求与验收
| 需求 | 可观察验收 |
|---|---|
| R1 修复成功回写长度限制 | 101/107/512 字符合成 ID 完整保存，Webhook/对账可以完整匹配，不截断 |
| R2 已接单不误重试 | 接单后写库失败、重启和恢复均不会再次外发；只恢复本地状态，不重复计数/释放额度 |
| R3 单个收件人拒绝不拖队 | 确认的永久拒绝终止该 enrollment，三次后第四个正常收件人可发送；临时错误有限延迟 |
| R4 真实通道限制受保护 | 真实 quota/429 保留暂停，未知错误不把正常联系人置无效；日志可区分阶段与业务码 |
| R5 历史失败可安全核实 | 默认 dry-run，已接单记录不直接重发；修复按步骤幂等，未知结果保留待核实 |
| R6 兼容现有可靠性契约 | A/B、租户隔离、工作日时区、跨日额度、锁/回调幂等有验证，不因本次修复退化 |

## 关键决策
优先修字段与接单回写边界；“跳过坏邮箱”只能作为明确收件人拒绝的分类能力，不能作为这次事故的主修复。详细状态机、字段、文件改动及执行顺序见 design.md、implement.md。

## 不在范围
生产迁移、生产修数、真实发信、重启、部署、推镜像、自动修改 .env、合并 main、回信监控、全面重做仪表盘、取消限流保护。

## 已知限制
第四封服务商具体 quota 错误码未知；扩容字段不能承诺余额或日额度限制自动解除。实际重复投递次数需服务商查询核实。本地实现已进入本 worktree，生产库尚未迁移。
