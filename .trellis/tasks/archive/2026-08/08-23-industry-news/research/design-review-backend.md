## ③ 额外发现

1. **design §3.3 `list_items` SQL 在 asyncpg 下会报错（实测）**。`(:categories IS NULL OR s.category = ANY(:categories))`：SQLAlchemy asyncpg 方言把重复命名参数编译为同一个 `$1`（实测 `SELECT 1 WHERE ($1 IS NULL OR s.category = ANY($1)) AND (NOT $2 OR ...)`），Neon PG16 预编译报 `asyncpg.exceptions.AmbiguousParameterError: could not determine data type of parameter $1`。**带 CAST 即可**：`(CAST(:categories AS text[]) IS NULL OR s.category = ANY(CAST(:categories AS text[])))`、`(CAST(:source_ids AS uuid[]) IS NULL OR s.id = ANY(CAST(:source_ids AS uuid[])))`（传 `None` 与 `list[str]` 均实测通过；uuid[] 接受 str 列表）；`(NOT :unread_only OR r.item_id IS NULL)` 的 bool 参数无需 CAST（实测通过）。仓库先例：`admin_work_schedule_service.py:267`（`ANY(CAST(:countries AS char(3)[]))`）、`tenant_hard_delete_service.py:212`（`CAST(:plan_ids AS uuid[])`）；另一条路是按条件动态拼 `where_parts`（`tenant_query_service` / `admin_collection_service` 的通行做法）。spec 红线：禁止 `:p::uuid` 写法（`database-guidelines.md:9`）。
2. **"`IntegrityError` 视为同稿"与每源单事务冲突**。PostgreSQL 在事务内任一语句出错后整个事务进入 aborted 状态，同一源后续 INSERT 全部失败（`current transaction is aborted`），该源会被记为失败而非"跳过一条"。design 的先 `SELECT` 再 `INSERT` 在单进程持锁下确实几乎不会触发冲突（同事务内能看见自己刚插的行，批内重复也被 SELECT 拦住），但若真触发就是整源失败。两种贴合 spec 的写法：`INSERT ... ON CONFLICT DO NOTHING`（不指定冲突目标即覆盖两条 UNIQUE；`rowcount == 0` 即同稿，可去掉预 SELECT，与 `database-guidelines.md:58`、`error-handling.md:30` 一致），或每条 `conn.begin_nested()`（先例 `wmt_lineage_repair.py:182`）。
3. **现役 `wmt_lineage_repair` 的锁只覆盖关系修复阶段**（`wmt_lineage_repair.py:217-229`），补评阶段在锁外——design 写"与 `wmt_lineage_repair` 同一写法"，如果目标是整轮互斥，这个先例并不提供。spec `workers.md:17` 的"必备模式 2"描述的也是事务级锁。
4. **`idle_in_transaction_session_timeout`（只读 `SHOW`）**：Neon 开发库 `5min`，生产（Sealos PG 16.4，UTC）`1h`，`statement_timeout` / `lock_timeout` 均为 0。影响 #2 方案 (B)；方案 (A)/(C) 不受影响。
5. **生产租户行业分布（只读）**：`lower(trim(industry))` → `pcb` 3 个、`电路板` 1 个，与 PRD"4 租户均可规范化为 PCB"一致；开发库仅 `PCB`。
6. **镜像安装不读 `uv.lock`**：`backend/Dockerfile:19` 为 `uv pip install --system .`（从 `pyproject.toml` 现场解析），`uv.lock` 只约束本地开发。新依赖的版本下限要写进 `pyproject.toml`，否则镜像装的是构建当天的最新版。
7. **`tenacity` 首次启用**：当前仅声明（`pyproject.toml:26`）无任何引用，仓库没有重试封装先例；`engagelab.py` / `openrouter.py` 都是无重试的单次调用 + 自定义异常。
8. **路由测试不跑 lifespan**：`httpx.ASGITransport`（`test_admin_config.py:128`、`test_sending_plan_routes.py:36`）不触发 lifespan，故新 worker 的 lifespan 分支与 `get_engine()` 都不会在路由测试里被执行；A7 的 lifespan 行为只能靠单元测试直接调用 `run_industry_news_fetch_loop` 验证。
9. **PR A 的 spec 同步点**（非清理）：`directory-structure.md:10`（lifespan 描述"分区维护 + 客户池修复循环"）、`:17`（workers 文件清单）、`:20`（`data/` 描述）、`:23`（scripts 清单）、`workers.md:7-12`（运行形态表）与 `:39-46`（检查清单）——A13 只提到 `workers.md` 补一行。
10. **`.env.example` 可改**：`backend/.env.example` 受 git 跟踪且不含真实凭证（已脱敏核对），A13 向其补两个变量说明不触碰 AGENTS.md §1 的 `.env` 红线；`backend/.env.local` 不动。
11. `paginated_response` 的 `has_more` 默认 `False`：若路由只传 `total`，前端分页组件若依赖 `has_more` 判断下一页会失效，务必按 `collection.py:83` 传 `has_more`。

## ④ 结论

design 的 lifespan 接入、Settings 写法、admin/tenant 子路由挂载、静态路由顺序、鉴权依赖选择、`beijing_time` 扩展、CLI 模式与新依赖兼容性均与仓库事实相符，可按图施工；**必须改的有三处**：(1) §3.3 的互斥方案——事务级锁在持锁事务结束即释放，按字面实现整轮无互斥，且现役 `wmt_lineage_repair` 先例本身也只锁第一阶段，应改为专用连接会话级锁（AUTOCOMMIT + `finally` unlock + 失败 `invalidate`）或单连接 + savepoint；(2) §3.3 `list_items` 的 `(:p IS NULL OR col = ANY(:p))` 写法在 asyncpg 下实测 `AmbiguousParameterError`，需 `CAST(:p AS text[] / uuid[])`，同时 "`IntegrityError` 视为同稿" 应改为 `ON CONFLICT DO NOTHING` 或 savepoint；(3) §3.5 "JOIN tenants 取行业"与 §3.3 SQL 的 `:industry` 参数互相矛盾，应改为 service 内先查 `tenants.industry` 再 `canonical_industry()`（先例 `tenant_messaging_service.py:72-79`）或给 `TenantAuthContext` 加带默认值的 `industry` 字段。§6 / B2 清理清单**漏了会让 PR B 直接失败的两项**——`internal_ops_service.py:4,11,37` 的导入（API 启动即崩）与 `admin_config_service.py:1463` 的 `intelligence_articles` 子查询（dashboard 500）——以及 `seed_demo_data.py`、`test_admin_config.py` 五端点用例、多处 spec 示例引用；另外 `maintain_partitions.py` 实际并无 `intelligence_articles` 条目，design 与 spec 的这一描述需纠正。
