# 发送计划收件人逻辑优化

## Summary

发送计划收件人步骤两项改动：群组选择器和合计从"人"改为"家公司"；收件人选取逻辑按 admin 联系人分类等级从高到低排序，每家公司最多取 8 个有邮箱的收件人，预览按公司汇总展示、可展开查看明细。

---

## Problem Frame

当前群组选择器显示"巴西LED照明行业（14 人）"，但群组的成员粒度是公司而非个人，"14 人"造成误解——实际是 14 家公司。

收件人预览直接展示群组内所有有邮箱的联系人，没有按公司限数、没有按等级排序。Admin 端已建好联系人分类体系（等级 A/B/X + is_sendable 开关 + 职位关键词匹配），但发送计划收件人选取逻辑未接入这套规则，导致收件人的选取和排序缺乏优先级控制。

---

## Requirements

**群组显示**
- R1. 群组选择器中，群组名称后的计数显示为"X 家公司"而非"X 人"
- R2. 收件人预览底部合计显示格式改为公司数和收件人数（如"合计 14 家公司，42 位收件人"）

**收件人选取规则**
- R3. 每家公司的收件人从该公司所有联系人中按以下规则选取：先按 admin 联系人分类等级 `sort_order` 从高到低排序，仅取 `is_sendable = true` 的等级，取前 8 个有邮箱的联系人
- R4. 未匹配到任何分类等级的联系人排在所有已分类联系人之后，仍可被选入（填充至 8 人上限）
- R5. 发送计划实际发送时，每家公司收件人不超过 8 个

**收件人预览**
- R6. 预览表格按公司汇总展示，每家公司一行，标注该公司入选的收件人数量
- R7. 公司行可展开查看该公司的收件人明细（联系人姓名、邮箱、分类等级）

---

## Acceptance Examples

- AE1. **Covers R3, R4.** 某公司有 12 个联系人：3 个 A 级（is_sendable=true）、4 个 B 级（is_sendable=true）、2 个 X 级（is_sendable=false）、3 个未分类。选取结果为 3 个 A 级 + 4 个 B 级 + 1 个未分类 = 8 人。X 级被排除因为 is_sendable=false。
- AE2. **Covers R3, R5.** 某公司有 5 个联系人全部是 B 级且 is_sendable=true 且有邮箱。选取结果为 5 人（不足 8 人则全部入选）。
- AE3. **Covers R1.** 群组包含 14 家公司，选择器显示"巴西LED照明行业（14 家公司）"。

---

## Success Criteria

- 群组选择器和预览合计正确反映公司数而非联系人数
- 收件人选取严格按等级优先、is_sendable 过滤、每公司 8 人上限执行
- 预览表格清晰展示每家公司的收件人数量和明细

---

## Scope Boundaries

- 不涉及手动选择和筛选器两种收件人来源的改动
- 不涉及 tenant 端暴露 `tenant_contacts.is_sendable` 配置界面
- 不涉及 admin 联系人分类规则本身的修改
- 不涉及发送逻辑（邮件实际发送流程）的改动

---

## Key Decisions

- 使用 `position_classification_levels.is_sendable` 作为"允许发送"判断依据，而非 `tenant_contacts.is_sendable`：后者当前无前端配置入口且默认全部为 true，admin 分类等级才是实际控制发送的规则
- 未分类联系人排最后但仍可入选：避免因分类覆盖不全而遗漏有效联系人

---

## Dependencies / Assumptions

- Admin 端联系人分类体系（等级、关键词、is_sendable）已部署且有数据
- `v_tenant_contact_classified` 视图可用于实时匹配联系人职位到等级
